Decision engines — where raw data becomes advice

Irrigation water balanceCORE

FAO-56 soil water balance. Tracks root-zone depletion daily:

depletion += (ET₀ × Kc) − effective rain

Advises irrigation when depletion reaches Readily Available Water. Crop- and soil-specific, so it can say “hold off, rain Thursday covers you.”

Allen et al. 1998Kc by growth stage

Crop health diagnosis

Evidence-weighted differential diagnosis over three signals:

① symptom keywords · ② whether recent weather actually favours the disease · ③ host crop

Returns a ranked list with confidence — never a single confident guess. Cannot flag a disease the weather contradicts.

explainabledegrades honestly

Market trend analysis

Aggregates mandi prices by day, computes 7/30-day movement, volatility and position within the recent range.

Emits a SELL / HOLD / WATCH signal comparing today against that range — explicitly not a forecast.

seeded data flagged

Risk & alert generation

Heat stress, frost, heavy rain, dry spells, high wind — each thresholded against the specific crop's tolerance.

Every alert carries a concrete action, deduplicated per farm/type/day.

Graceful degradation

Weather provider down → serve the last stored bundle with a visible “N hours old” warning. Market API down → stored history. No Plant.id key → rule engine alone. The dashboard resolves every section with Promise.allSettled, so one failing upstream never blanks the page.

Privacy & isolation

Every database query is scoped by the authenticated user id; another farmer's farm returns 404, not 403, so the API does not leak which ids exist. No personally identifying data is sent to any third party — only latitude, longitude and crop name.

Why one runtime

An earlier design placed the engines in a separate Python service. Both the water balance and the diagnostic engine are deterministic rule systems needing no ML runtime, so folding them into Node removed a network hop, a deployment target and a failure mode.
